# 易理明灯 RAG 架构 v4.0 设计文档

> 状态: 设计中 | 日期: 2026-07-19 | 作者: 闫海洋 PM + Claude Code

## 一、背景与目标

### 1.1 当前状态（v3.1）

- 27,115 条知识已入库 ChromaDB（fortune_books 集合）
- 44,493 条问真命盘待入库
- Embedding 模型存在严重架构缺陷：`embedder.py` 硬编码模型加载逻辑，忽略 `model_name` 配置参数
- 检索链路：单次向量搜索 → 无结果才用 jieba 关键词兜底 → 无重排序 → 无查询增强
- 分块策略：固定 500 字 + 50 字重叠，无古文语义感知
- 评估体系：无，检索质量完全不可知

### 1.2 核心问题

1. **模型不可控**：配置文件指定 BGE-large-zh-v1.5（1024 维），实际加载的是硬编码的 ModelScope GTE-base（768 维），降级又变成 MiniLM（384 维）。三个模型维度不同，查询崩溃。
2. **检索 = 搜一次**：没有查询理解、没有混合检索融合、没有重排序、没有反思回路。
3. **知识无结构**：7 万条知识平铺在向量库，见树不见林。
4. **无法进化**：没有评估基准，改好了改坏了都不知道。

### 1.3 目标

打造算命/玄学领域最强的知识检索系统：
- 用户问任何玄学问题，系统精准命中古籍依据 + 同类命例
- 每条 AI 回答附带溯源引用
- 支持独立的知识搜索浏览
- 检索质量可量化评估，持续进化

### 3.2 分层详解

#### Layer 1: Query Enhancement（查询增强）

**目的**：用户口语 → 专业检索语言，提升检索命中率。

```
输入: "我属虎的，今年本命年会不会很倒霉"
输出（改写后）:
  - 主查询: "属虎者本命年犯太岁的命理分析与化解方法"
  - 子查询1: "寅虎本命年 值太岁 影响"
  - 子查询2: "本命年化解 穿红 拜太岁 古籍记载"
```

**实现**：
- 用 DeepSeek-v4-flash（快，便宜）做查询改写和拆解
- 拆解策略：按"理论依据 + 化解方法 + 同类案例"三维拆解
- 每个子查询携带 category filter 缩小搜索范围

#### Layer 2a: GraphRAG Engine（全局知识图谱）

**目的**：把离散的知识点构建成有层级、有关系、可全局理解的知识网络。

**实体类型**：
| 类型 | 示例 | 数量(估) |
|------|------|-----------|
| 天干 | 甲、乙、丙... | 10 |
| 地支 | 子、丑、寅... | 12 |
| 五行 | 金、木、水、火、土 | 5 |
| 十神 | 正官、七杀、正印... | 10 |
| 神煞 | 天乙贵人、驿马、桃花... | ~50 |
| 格局 | 正官格、七杀格、从格... | ~100 |
| 经典 | 《滴天髓》《渊海子平》... | ~30 |
| 命例 | 44,493 条问真命盘 | 44,493 |
| 名人 | 1005 条名人命例 | 1,005 |

**关系类型**：
| 关系 | 示例 |
|------|------|
| 生 | 木→火 |
| 克 | 金→木 |
| 合 | 甲己合土 |
| 冲 | 子午冲 |
| 刑 | 丑戌刑 |
| 害 | 子未害 |
| 十神对应 | 日主甲见庚 = 七杀 |
| 古籍出处 | "财星宜藏不宜露" ← 《滴天髓》 |
| 命例类似 | 马云(身弱财旺) ↔ 用户 X |

**构建流程**：
1. 实体抽取：用 LLM 从 27,115 条知识 + 44,493 条命盘中抽取实体
2. 关系抽取：从生克合冲 + 古籍理论中抽取关系
3. 社区发现：Leiden 算法聚类，形成概念社区（如"身弱财旺组""伤官配印组"）
4. 社区摘要：LLM 为每个社区生成摘要描述

**存储**：SQLite（轻量，单文件，够用），无需 Neo4j 等重型图数据库。

**检索方式**：
- 全局检索：匹配社区摘要 → 返回整个社区的代表性内容
- 局部检索：图谱遍历 → 从用户命盘出发，沿关系链找到相关理论
- 命例检索：命盘相似度 → 找 TOP-3 相似命例

#### Layer 2b: BGE-M3 Dense + Sparse

**为什么选 BGE-M3**：
- BAAI（北京智源）出品，中文 Embedding 目前 SOTA
- 1024 维，支持 Dense（语义）+ Sparse（词汇）双表征，单模型双输出
- 支持多语言，8K 上下文长度（古文长段落也能一次编码）
- MIT 许可，商用友好

**Dense 检索**：
- 1024 维向量，余弦距离
- 覆盖语义相似但字面不同的情况
- 例：用户说"赚不到钱" ↔ 知识库"财星不显，求财艰辛"

**Sparse 检索（BGE-M3 原生）**：
- 每个文档输出 learned sparse weights（不是传统 BM25，是模型学出来的重要 token 权重）
- 覆盖专业术语精确匹配
- 例："伤官见官"必须精确匹配

**为什么不用 BM25**：BM25 基于词频统计，古文用词和现代汉语差距大，BM25 效果差。BGE-M3 的 learned sparse 是在大量中文语料上训练的，理解现代汉语和古文的术语对应关系。

#### Layer 3: RRF Fusion

**Reciprocal Rank Fusion** 是公认最好的混合检索融合算法：

```
RRF_score(d) = Σ 1/(k + rank_i(d))

其中:
  k = 60 (经典参数)
  rank_i(d) = 文档 d 在第 i 个检索结果列表中的排名
```

**为什么不用 score 加权融合**：不同检索源的 score 尺度不同（余弦距离 vs 图谱相似度），不可直接比。RRF 只关心排名，天然跨源可比。

#### Layer 4: Reranking（精排）

**BGE-Reranker-v2-m3（Cross-Encoder）**：
- 输入 (query, doc) pair，输出精确的相关性分数
- 比向量检索（Bi-Encoder）精度高 15-20%
- 计算量大，只在 Top-20 候选上运行

**阈值策略**：
- Score ≥ 0.75：直接采用
- Score 0.5-0.75：标记为"参考"
- Score < 0.5：丢弃

#### Layer 5: Self-RAG Reflection（反思回路）

**核心逻辑**：

```python
def self_rag_reflect(query, top5_results):
    reflection_prompt = f"""
    用户问题: {query}
    检索到 {len(top5_results)} 条结果:
    {format_results(top5_results)}
    
    请评估:
    1. 这些结果是否充分覆盖了问题的各个维度？
    2. 缺少哪些方面的信息？
    3. 是否需要补充检索？
       - 如果缺理论依据 → 补搜古籍
       - 如果缺同类命例 → 补搜命例库
       - 如果缺化解方案 → 补搜风水/择日
    """
    
    reflection = llm.judge(reflection_prompt)
    
    if reflection.needs_more and reflection.round < 2:
        new_queries = reflection.suggest_queries
        additional = parallel_retrieve(new_queries)
        top5 = rerank(merge(top5_results, additional))
    
    return top5, reflection
```

**关键约束**：最多 2 轮反思，避免无限循环和延迟。

#### Layer 6: LLM Generation

**Prompt 模板核心**：

```
你是一位精通命理的易学大师。基于以下信息回答用户:

【用户命盘】
{user_bazi}

【相关知识（来自古籍和命例库）】
{top5_knowledge_with_citations}

要求:
1. 每条论断必须标注出处（古籍名/命例ID）
2. 如果你不确定，明确说明"此为推测"
3. 给出可操作的行动建议
```

## 四、Embedding 领域微调

### 4.1 为什么需要微调

通用 BGE-M3 在中文表现很好，但它不理解：
- "伤官见官，为祸百端" v.s. "伤官配印，贵不可言" → 都是伤官，格局天差地别
- "甲木参天" v.s. "甲木无根" → 同样是甲木，旺衰两重天
- 同样的八字术语在不同语境下可能指代完全不同的意思

### 4.2 微调数据

| 数据源 | 数量 | 用途 |
|--------|------|------|
| 问真命盘 | 44,493 | 命盘→特征对比学习 |
| 古籍知识库 | 27,115 | 古文→现代文对齐 |
| 用户反馈 | 持续积累 | 真实查询→满意结果 |

### 4.3 微调方法

**对比学习（Contrastive Learning）**：
- 正样本对：(命盘描述, 匹配的古籍理论)
- 负样本对：(命盘描述, 不匹配的古籍理论)
- 训练方法：InfoNCE Loss，使正样本 embedding 靠近、负样本远离

**LoRA 微调**（Low-Rank Adaptation）：
- 只训练低秩矩阵（~0.1% 参数），不修改原始模型
- 可插拔：基础 BGE-M3 保留，LoRA 权重模块化加载
- 每月用新反馈数据更新 LoRA 权重

### 4.4 微调流程

```
原始 BGE-M3 (frozen)
    +
LoRA 适配器 (trainable)
    │
    ├─ 训练数据: 命盘-古籍匹配对
    ├─ 验证集: 人工标注 200 条
    ├─ 评估指标: NDCG@5, MRR
    │
    ▼
每月迭代: 新反馈数据 → 更新 LoRA → A/B 测试 → 上线
```

## 五、评估体系

### 5.1 三层评估

```
Layer 1: 自动评估（每次代码变更触发）
  ├─ NDCG@5, MRR, Recall@20
  └─ 基准数据集: 人工标注 200 条

Layer 2: AI 评估（每周）
  ├─ DeepSeek 自动评判 1000 条真实查询
  └─ 评分维度: 相关性、完整性、准确性

Layer 3: 用户反馈（实时）
  ├─ 👍/👎 → 直接信号
  ├─ 追问率 → 检索不够好的间接信号
  └─ 引用点击率 → 知识溯源是否被信任
```

### 5.2 基准数据集构建

1. **专家标注（200 条）**
   - 覆盖 8 个领域（八字/紫微/风水/解梦/面相/奇门/姓名/择日）
   - 每个领域 25 条 query
   - 标注：query → relevant_docs (1-3条) → 相关性等级 (0-3)
   
2. **AI 扩展（800 条）**
   - 基于 200 条人工标注
   - LLM 生成同义改写 + 反向改写
   - 人工抽检（20%）确认质量

3. **在线验证**
   - 新模型上线前，A/B 测试 7 天
   - 对比指标：用户点赞率、引用点击率、追问率
