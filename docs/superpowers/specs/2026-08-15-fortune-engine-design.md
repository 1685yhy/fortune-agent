# 易理推理内核（Engine）设计文档

- 日期：2026-08-15
- 状态：已获用户认可（方案 A：独立分支 engine-v1 + 六阶段门禁）
- 关联项目：易理明灯 /mnt/e/fortune-agent
- 作者：主会话设计，用户 2026-08-15 逐块确认

## 1. 背景与目标

用户提出"推理引擎"构想：充分理解各术数体系（八字/紫微/六爻/奇门/六壬等）的底层原理，拿到输入后自行排盘、按规则推演、多体系组合互证，最终给出**带出处与完整推理链**的结论——区别于现有"排盘 → RAG 检索古籍 → LLM 包装"的检索式模式。

与用户达成的关键共识：

- **排盘 = 数学**：确定性计算，同输入必同输出，可验证（历法用 lunar-python + 既有引擎）
- **断语 ≠ 定理**：命理断语无标准答案，无法验证"准"；古籍之间互相分歧是常态
- **不承诺"预测更准"**，承诺**更严谨、更有依据、更可解释、更稳定**（同盘必同断）
- **检索降级**：从"找答案的主角"降为"找证据的配角"（举证）

## 2. 定位与边界

- 本工程是一个**独立推理内核**，与现有对话产品完全解耦
- 只读复用现有能力：排盘引擎、向量检索、引用系统、LLM client；**零修改旧文件**
- 不做：预测准确率承诺、替换现有产品、改动线上功能
- 验收语言以"让人信"为核心（具体、有推理、稳定、有出处），而非"算得准"

## 3. 总体架构（一条主链）

```
输入（出生信息 / 问事）
 → ① 排盘层      复用现有 engines（八字/紫微/六爻/奇门）+ 新写六壬起课
 → ② 规则推演层  新写：规则库 + 推演引擎，每步记录成"推演链"
 → ③ 举证层      检索降级：按推演要点查古籍，取原文出处（复用 faiss_retriever + citation）
 → ④ 综合层      LLM 基于推演链 + 证据生成解读（非检索拼接）
 → ⑤ 多体系合成  共识/分歧分析 → 最终报告
输出：推演链 + 结论 + 出处（每步可回放、可审计）
```

关键变化：检索从"找答案"降为"找证据"；推演层位于排盘与检索之间（先算清楚盘面事实，再带精确要点查书）。

## 4. 代码布局与隔离

- git 分支：`engine-v1`（从 main 拉出，永久不动 main）
- 新代码全部位于新目录 `src/engine/`：

```

│   ├── qiongtong.py  # 穷通宝鉴 10日主×12月令 = 120 格查表

│   └── shishen.py    # 十神生克组合规则
```

## 5. 考卷体系（质量地基，阶段 0）

- 考卷来源优先级：
  1. **古籍原文命例**（《滴天髓》《穷通宝鉴》等书内自带，旁边写有标准断语）——主考卷
  2. 现有 bazi_case 4.9k ——**必须先核查来源**：来源可追溯 + 期望答案明确才收录，查不清一律弃用
- 考卷格式：输入（年月日时 + 性别）→ 期望输出（格局/用神/关键断语）
- 两级考试：
  - 单元级：单张规则表单独考（如穷通宝鉴 120 格逐格验证）
  - 端到端：全链路推演考
- **门禁制度**：每阶段考卷全过才进下一阶段；考试结果留档作为证据（与强制验证规则一致）

## 6. 六个阶段与验收门禁

| 阶段 | 内容 | 过闸标准 |
|---|---|---|
| 0 考卷 | 命例数字化 + 来源核查 | 考卷库可跑分，来源可追溯 |
| 1 八字规则库 | 穷通宝鉴 120 格 / 子平真诠格局 / 滴天髓原理 | 三本书考卷全过 |
| 2 推演链引擎 | 排盘→推演→举证→综合 | 全链路考卷全过 + 推演链可回放 |
| 3 其他体系 | 紫微/六爻/奇门/六壬（新写起课） | 各体系考卷全过 |
| 4 合成层 | 多体系共识/分歧 | 分歧如实呈现，出处齐全 |
| 5 对比报告 | 同案例 检索式 vs 引擎式并排 | 用户亲眼验收 |

## 7. 数据流、分歧处理与测试

- 规则未覆盖：`coverage.py` 明确标注"未覆盖"，绝不装懂
- 古籍打架：两说并存、各带出处，由合成层权衡（专业做法，非挑一弃一）
- 测试：单元（每张表）+ 端到端（考卷跑分）+ 对比报告，全自动运行，证据留档

## 8. 分支与版本管理规范（重点）

1. **main 是生产分支**：线上部署只从 main 走；engine-v1 永不直接触碰 main
2. **engine-v1 从 main 拉出**：只提交 `src/engine/` 与本设计相关文档，其余一律不 add
3. **同步方向单向**：main → engine-v1 允许（`git merge main`，生产热修可流入）；engine-v1 → main 仅在用户明确拍板后执行
4. **提交纪律**：每阶段一个里程碑提交，提交信息规范（`feat(engine): ...`）；不 push 远程，除非用户要求
5. **现有未提交改动**（如 `logs/audit.log`、既有计划文档）不属本工程，不打包、不误提交
6. **合回 main 的条件**：阶段 5 对比报告用户验收通过 + 用户明确拍板
7. 覆盖清单与考卷记录一并纳入版本管理（全流程可审计）

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 考卷来源不可靠 | 阶段 0 核查，不可追溯即弃用，主考卷用古籍原文命例 |
| 规则提取错误 | 考卷门禁兜底，单元级考试精准定位错表 |
| 项目并行修改冲突 | 独立目录 + 单向同步（main→engine-v1），合回前 diff 审查 |
| 检索降级后质量倒退 | 对比报告（阶段 5）以用户验收为准 |
